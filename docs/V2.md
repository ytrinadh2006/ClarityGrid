# ClarityGrid V2

V2 moves the project from a one-shot dashboard toward a small reusable analysis workspace.

## What was added

### Local analysis history

A small SQLite database stores saved analysis summaries locally. I chose SQLite because this is a single-user student application and it does not need a database server.

### SQL workspace

The uploaded table can be queried through a small read-only SQL panel. The data is copied into an in-memory SQLite database for the query, so the original file is not changed. Only `SELECT` and `WITH` queries are accepted.

I kept this deliberately simple. The goal is to make SQL useful inside the analysis workflow, not to build another database product.

### Trend analysis

When a date-like column and numeric measure are available, the app aggregates values by date and shows a rolling mean.

### IQR anomaly detection

The anomaly detector uses the familiar interquartile-range rule:

`lower = Q1 - 1.5 × IQR`

`upper = Q3 + 1.5 × IQR`

It is a statistical screen, not a claim that every flagged point is a real business problem.

### Baseline forecasting

The forecast uses linear regression on time-indexed observations. It is intentionally a baseline that is easy to inspect rather than a replacement for dedicated forecasting methods.

### Better ML evaluation

The ML lab now shows the normal train/test comparison plus a small cross-validation check. Binary classification can also show ROC-AUC, and classification experiments expose the confusion matrix.

This was added because a single accuracy or R² value can be misleading on its own. The project still avoids AutoML and keeps the models understandable.

## What I learned from V2

An analytics application needs more than charts. It needs reproducibility, validation, saved state and a clear separation between data handling and UI code. Adding SQL and cross-validation also made the workflow feel closer to how I would actually explore a new dataset.

## Still deliberately out of scope

I have not added a large LLM layer, vector database, distributed processing or a cloud architecture just to make the project sound bigger. Those are possible future directions, but the current version should stay understandable and testable.

## Next sensible step

The next version could add a small API layer, model persistence and generated reports after the current workflow is stable.
